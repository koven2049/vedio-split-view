# 实验日志

每条：假设 → 改动 → 计数 → 配对 p75（Fast 4G，10 次，A/B 交替）→ 是否保留。

## 1. 列表接口只读卡片需要的列（commit 3d1a185，保留）

- **假设**：`/api/videos` 读整行，每行约 270 KB 大文本白读一遍；改成 `load_only` 只读卡片列，预计列表接口降一个数量级，资源库页省 40–60 ms。
- **改动**：`_LIST_COLUMNS = load_only(...)` 用在 `/api/videos` 和 `/api/videos/public`；详情接口 `defer` 掉 `raw_transcript` / `subtitle_json`。
- **计数**：响应字节不变（7617 B / 22984 B / 24701 B），黄金比对 10 个接口逐字节一致（时间戳字段除外）。
- **API p75**（回环，40 次，配对）：列表 20 条 69.1 → 10.1 ms（−85%）；100 条 160.6 → 11.6 ms（−93%）；详情 4.0 → 3.5 ms。
- **页面 p75**（配对，A=基线 / B=本步 + 同提交的 UI 改动）：资源库 1182 → 1150 ms（−2.7%）；详情 1166 → 1165 ms（持平）；文档 1119 → 1102 ms（−1.5%）。
- **结论**：服务端耗时降得很多，但页面被 474 KB 的未压缩 bundle 盖住了，所以页面上只看到列表省下的那几十毫秒。保留。

## 2. 开启 gzip（commit 65c5e3e，保留）

- **假设**：bundle 474 KB 没压缩，gzip 后约 140 KB；4 Mbps 下能省约 0.65s。
- **改动**：`GZipMiddleware(minimum_size=1024, compresslevel=6)`。Starlette 默认跳过 `text/event-stream`，SSE 进度流不受影响（有测试打到真实的流路由）。
- **计数**：传输字节 详情 664 → 270 KB，资源库 510 → 147 KB，文档 516 → 147 KB。
- **页面 p75**（配对，A=基线 / B=1+2）：

| 页面 | A | B | 降幅 |
|---|---|---|---|
| 详情 | 1172 | 440 | −62.5% |
| 资源库 | 1205 | 447 | −62.9% |
| 文档 | 1134 | 433 | −61.8% |

  原始数据：`bench/step2-*.json`。
- **结论**：超额完成「降一半」的目标。棘轮上限按 B 记入 `bench/ceilings.json`。

## 3. 路由级代码拆分（React.lazy，已回退，未提交）

- **假设**：首包 474 KB 里各页面代码约 120 KB；按路由拆开后，每页只下载自己那份，gzip 后首包少约 30 KB，预计省 30–50 ms（多一次 chunk 往返会吃掉一部分）。
- **改动**：`App.tsx` 里 9 个页面改成 `lazy(() => import(...))`，外包 `<Suspense>`。
- **计数**：主 chunk 334 KB（未压缩）；传输字节只降 12–25 KB；**请求数 5 → 16（详情）/ 7 → 18（资源库）/ 4 → 8（文档）**——Rollup 把共用的 lucide 图标等拆成了一串小 chunk，入口 chunk 解析完才能发现它们，形成串行瀑布。
- **页面 p75**（配对，A=步骤 2 / B=本步）：详情 449 → 679 ms（+51%）；资源库 458 → 687 ms（+50%）；文档 424 → 658 ms（+55%）。
- **结论**：变慢，回退。这也说明在 20 ms RTT 下，「请求数」比「字节数」更要紧。剩下能省的字节上限约 25 KB（约 50 ms），还要先用 `manualChunks` 收拢小 chunk 才可能转正，边际收益小，交给用户决定做不做。
